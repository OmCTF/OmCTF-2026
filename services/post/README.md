# Связь: развёртывание

Сервис рассчитан на Linux/amd64 и Docker Compose v2. В одном стеке работают
Go API, Rust runtime, React frontend, PostgreSQL, Redis и объектное хранилище.
Команды ниже выполняются из каталога с `compose.yaml`. На каждом vulnbox
должен быть свой экземпляр стека и свои секреты. Команды настройки TLS
выполняются от root.

## Что подготовить

- Docker Engine с плагином `docker compose`, `python3` и `openssl`.
- Домен для каждого vulnbox. В браузере участника домен должен разрешаться в
  адрес этого vulnbox, например `svyaz-42.ad.example -> 10.60.1.42`.
- Действительный сертификат и закрытый ключ для этого домена либо внешний
  HTTPS-прокси. Сервис не выпускает сертификаты и не занимает TCP-порт 80.
- Доступ участников к HTTPS-адресу и к UDP-порту голосового сервиса. Для
  WebRTC нужен IPv4, достижимый из сети участников; одного домена и HTTPS
  недостаточно.

По умолчанию веб слушает TCP `18080`, голосовой транспорт UDP `20000`.
База данных, Redis и хранилище наружу не публикуются. Если порт голосового
транспорта меняется, задайте `VOICE_UDP_PORT` в `.env` до запуска и откройте
этот UDP-порт в правилах сети.

## Вариант A: TLS внутри сервиса

Используйте этот вариант, если сертификат и ключ доступны на самом vulnbox.
DNS-01 и продление сертификата организуются снаружи; сюда передаются уже
готовые файлы. Пример для прямого доступа к порту `18080`:

```sh
sh deploy/tls/configure.sh \
  https://svyaz-42.ad.example:18080 \
  /path/to/fullchain.pem \
  /path/to/privkey.pem \
  10.60.1.42
sh deploy/start.sh
```

Аргументы `configure.sh`: публичный HTTPS-origin, файл цепочки сертификатов,
файл закрытого ключа, IPv4 для WebRTC, необязательные TCP-порт веба и IP
привязки веба. По умолчанию последние два аргумента равны `18080` и
`0.0.0.0`. Для локального reverse proxy можно указать `127.0.0.1` как
шестой аргумент, но прокси должен обращаться к сервису по HTTPS.

Скрипт запускается от root. Он проверяет домен в сертификате, срок действия
и соответствие ключа, копирует файлы в `tls/runtime/` с правами
`101:101/600`, создаёт случайные пароли при первом запуске и записывает
`APP_ENV=production`, `APP_ORIGIN`, `COMPOSE_FILE` и сетевые настройки в
`.env`. Сертификат не выпускается автоматически.

После обновления сертификата запустите ту же команду с `TLS_RELOAD=1`:

```sh
TLS_RELOAD=1 sh deploy/tls/configure.sh \
  https://svyaz-42.ad.example:18080 \
  /path/to/fullchain.pem \
  /path/to/privkey.pem \
  10.60.1.42
```

Добавьте её в hook системы, которая продлевает сертификат. `TLS_RELOAD=1`
перезагружает конфигурацию уже запущенного Nginx; при первоначальной
установке без работающего контейнера не задавайте эту переменную.

## Вариант B: TLS на внешнем прокси

Если HTTPS завершается у организаторов, контейнеру `web` не нужны сертификаты.
Прокси передаёт весь HTTP-трафик, включая WebSocket Upgrade, на веб-порт
сервиса. В `.env` после `sh deploy/init-secrets.sh` задайте:

```dotenv
APP_ENV=production
APP_ORIGIN=https://svyaz-42.ad.example
ALLOW_PUBLIC_HTTP=0
COMPOSE_FILE=compose.yaml
WEB_BIND_IP=127.0.0.1
WEB_PORT=18080
VOICE_BIND_IP=0.0.0.0
VOICE_ANNOUNCE_IP=10.60.1.42
```

Затем выполните `sh deploy/start.sh`. В этом варианте прокси должен
предоставлять браузеру действительный сертификат, сохранять исходный
`Host`, пропускать `Origin` без изменения и поддерживать `wss://`.
Значение `WEB_BIND_IP=127.0.0.1` подходит только для прокси на том же
vulnbox. Если прокси находится на другом узле, привяжите веб к адресу,
доступному **только прокси**, и ограничьте входящий TCP firewall-ом.

Не включайте оба варианта одновременно. `APP_ORIGIN` всегда должен в
точности совпадать с адресом в браузере: без `:443` при стандартном HTTPS,
но с `:18080` при прямом доступе к этому порту.

## Проверка

```sh
docker compose ps
docker compose logs --tail=100 migrate api rust web
curl -fsS https://svyaz-42.ad.example:18080/health/ready
```

При варианте B используйте внешний URL без `:18080`, если прокси слушает
`443`. Все основные контейнеры должны быть healthy, миграция должна
завершиться с кодом 0. Проверяйте WebRTC отдельно из браузера участника:
HTTPS обеспечивает secure context, но медиапотоку всё ещё нужен доступный
UDP-адрес из `VOICE_ANNOUNCE_IP`.

## Чекер ForcAD

Чекер поставляется отдельно от сервиса. Если ForcAD передаёт адрес
`10.60.1.N`, а сертификат привязан к домену, задайте ему, например:

```dotenv
SVYAZ_HOST_TEMPLATE=svyaz-{octet}.ad.example
SVYAZ_SCHEME=https
SVYAZ_PORT=18080
```

`{octet}` заменяется последним октетом IPv4; для `10.60.1.42` получится
`svyaz-42.ad.example`. DNS на стороне воркеров ForcAD должен разрешать этот
домен в нужный vulnbox. Если ForcAD передаёт домен сразу, шаблон не нужен.
При внешнем прокси на `443` установите `SVYAZ_PORT=443`.

## Секреты и обновления

`.env`, `tls/runtime/`, тома PostgreSQL и хранилища не входят в архив
участников и не должны переноситься между командами. Не публикуйте их и
не записывайте пароли в общий образ. Повторный `sh deploy/start.sh`
сохраняет существующие секреты и данные в томах.

Для обновления файлов сервиса сохраните `.env` и `tls/runtime/`, замените
только код и бинарники, затем выполните `sh deploy/start.sh`. Не удаляйте
тома Compose при обновлении. При смене TLS-режима проверьте
`COMPOSE_FILE` и `APP_ORIGIN` перед перезапуском.
