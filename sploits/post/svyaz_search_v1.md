# svyaz_search_v1.py

The checker uses the flag as the filename of a private attachment. The private
document does not appear in search results, but its terms affect relevance
statistics for the whole guild. For each of the 31 unknown characters, the
sploit prepares two public candidate messages, then compares the order of the
first two search pages with `author_id` restricted to its own account. One
candidate changes the continuation order. Pairs of candidates reduce request
count without unstable floating-point sums. The final `=` is fixed by the flag
format.

The script skips guilds recognizable as the media or sound flagstores. It uses
sequential requests per character, edits the same two probe messages at each
step, and deletes them when finished. It repeats measurements and confirms the
selected character before advancing. Successful results are cached
with mode 0600 for five minutes, so a later S4DFarm run does not repeat the
probing in the same guild. The service scopes public relevance statistics to
the requested author, so other attackers' probe messages do not affect its
cursor comparisons.

**Status:** five independent Linux containers from separate source IPs
concurrently recovered the same local test flag in 64.8 seconds. The service
and the sploit were built from the current branch. Competition-scale latency
may change this runtime.
