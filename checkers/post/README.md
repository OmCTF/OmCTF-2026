# Чекер «Связи» для ForcAD

Это файлы только для организаторов. Не добавляйте их в архив участников.

- `post/checker.py`: сценарии `CHECK`, `PUT`, `GET` и вердикты ForcAD.
- `post/svyaz_lib.py`: все API-вызовы чекера, сессии, WebSocket, PNG и WAV.
- `post/assets/`: шрифт и лицензия для генерации и чтения PNG-флагов.
- `requirements.txt`: зависимости Python для контейнера чекеров.

## Конфигурация

```yaml
tasks:
  - name: post
    checker: post/checker.py
    checker_type: pfr
    checker_timeout: 25
    puts: 1
    gets: 1
    places: 3
```

`puts: 1` означает один новый флаг на команду за раунд. `places: 3` даёт ForcAD
выбрать один из трёх флагсторов для каждого `PUT`; его номер затем передаётся
в `GET`. Выбор может различаться у команд в одном раунде. При `round_time: 60`
и `flag_lifetime: 5` флаги действительны пять раундов только в платформе;
сервис не удаляет их автоматически. `gets: 1` проверяет один прежний флаг.

Чекер запускается с аргументами Hackerdom/ForcAD: `check <host>`,
`put <host> <flag_id> <flag> <place>`, `get <host> <private_receipt> <flag> <place>`.
HTTP-порт по умолчанию 18080, переменная `SVYAZ_PORT` его переопределяет.
`checker.py` должен быть доступен на чтение и исполнение пользователю
контейнера чекеров. Файлы на диске для хранения флагов чекер не использует.

## Что проверяет CHECK

`CHECK` каждый раз создаёт три новых аккаунта и проверяет обычные пользовательские
сценарии, не связанные с конкретным флагом:

1. Регистрация и вход двух основных пользователей; для санкций создаётся третий.
2. Выдача HTML веб-приложения на корневом URL.
3. Создание сервера, получение списка каналов и ролей, создание приглашения и
   вход второго пользователя по нему.
4. Публикация сообщения, чтение его другим участником, поиск и воспроизведение
   события через Rust realtime WebSocket.
5. Создание закрытой категории и текстового канала; приглашённый пользователь
   должен получать отказ при обращении к каналу.
6. Загрузка PNG, ожидание обработки медиа-воркером, отправка вложения в сообщении
   и скачивание теми же байтами другим участником.
7. Создание голосового канала, загрузка и чтение клипа soundboard, получение
   доступа к голосу и успешный вход в Rust voice WebSocket.
8. Заявка в друзья, её принятие, создание DM, отправка и чтение личного сообщения
   вторым пользователем, а также редактирование и удаление сообщения в DM.
9. Редактирование и удаление сообщений автором и модератором, запрет чужого
   редактирования, конфликт устаревшей версии и tombstone в истории.
10. Управление сервером: переименование, аудит, создание/изменение/перестановка/
    назначение/удаление ролей, категории и каналы, порядок каналов, перезаписи
    прав, просмотр и отзыв приглашения, удаление участника, подтверждённая
    передача владения и удаление отдельного тестового сервера.
11. Webhook: создание, список, доставка сообщения, ротация секрета, отказ
    старому секрету и удалённому webhook.
12. Уведомления: настройки пользователя, правила уровня пользователя/сервера/
    канала, доставка в inbox, claim, отметка прочтения и удаление правил.
13. Модерация: текстовый и голосовой mute, отзыв санкций и восстановление прав,
    ban с последующим возвратом участника и kick.

Таким образом, `CHECK` проверяет авторизацию, Go API, права доступа, поиск,
Rust realtime, медиа-хранилище и воркер, звуковые клипы, голосовую сигнализацию и социальные
функции. Простого ответа `/health` недостаточно для вердикта `OK`. Эти сценарии
выполняются **каждый** раунд, а не выбираются случайно: пять локальных прогонов
заняли 1.8–3.4 с, поэтому ротация проверок не нужна. Лимит ForcAD составляет 25 с.

## PUT и GET

`PUT` создаёт новый аккаунт и сервер, приглашение, закрытую категорию и канал.
Затем кладёт флаг только в выбранный ForcAD флагстор:

| place | Хранилище | Размещение | Проверка GET |
| --- | --- | --- | --- |
| 1 | `media` | Флаг нарисован в нижней полосе PNG закрытого канала | Вход владельцем, скачивание файла, распознавание глифов |
| 2 | `search` | Имя файла вложения в закрытом канале | Вход владельцем, чтение сообщения и имени файла |
| 3 | `sound` | Произнесённые символы в приватном клипе soundboard голосового канала | Вход владельцем, скачивание и распознавание WAV |

`GET` сравнивает извлечённое значение с флагом, полученным от ForcAD. Другие
подсистемы проверяет `CHECK`, поэтому выбранный флагстор не определяет весь
объём проверки сервиса.

## Attack data

В режиме `pfr` успешный `PUT` пишет в `stdout` только код приглашения
без JSON-обёртки. ForcAD отдаёт эту строку участникам как `attack_data`.
Ключ задачи в выдаче ForcAD: `post`.
После входа по приглашению публичные каналы и их содержимое доступны через
обычный API сервиса. Тип флагстора и ID приватных объектов не публикуются.

В `attack_data` нет флага, пароля владельца и ID приватного канала. Приватный
receipt выводится в `stderr` и содержит `owner.login`, `owner.password`,
`private_room`, а также ID объекта, необходимого для `GET`. Его нельзя
публиковать как `attack_data` или добавлять в логи участников.

## TLS-домены

Если ForcAD передаёт чекеру адрес `10.60.1.N`, а сертификат выписан на домен,
задайте `SVYAZ_HOST_TEMPLATE` с плейсхолдером `{octet}` (последний октет
IPv4), например `svyaz-{octet}.ad.example`. DNS должен разрешать полученный
домен в адрес соответствующего vulnbox. Если ForcAD сразу передаёт домен,
шаблон не нужен.

Для HTTPS задайте `SVYAZ_SCHEME=https` и `SVYAZ_PORT`: `18080` при
прямом доступе к сервису или `443` при внешней TLS-прокси. На порту 443
чекер не добавляет `:443` к `Origin`, чтобы он совпадал с `APP_ORIGIN`.

## Вердикты и сообщения

| Код | Когда используется | Что видят участники |
| --- | --- | --- |
| `101 OK` | Сценарий выполнен | При `PUT` только код приглашения |
| `102 CORRUPT` | Прежний флаг отсутствует или отличается | `Could not read previously stored data` |
| `103 MUMBLE` | Сервис отвечает, но пользовательский сценарий не работает | Английская фраза об области сбоя: авторизация, серверы, сообщения, права, вложения, голос, DM, управление, webhook, уведомления или модерация |
| `104 DOWN` | Нет соединения с хостом | `Cannot connect to service` |
| `110 CHECKER_ERROR` | Неверные аргументы, receipt или неожиданная ошибка чекера | `Checker error` |

Сообщение об ошибке в `stdout` намеренно не содержит точный URL, HTTP-код,
ID ресурса, пароль или флаг. Оно даёт направление для починки, но не указывает конкретную
проверку и тем более эксплойт. Подробная диагностика (`метод`, `маршрут`,
`HTTP-код`, внутреннее условие) идёт в `stderr` для организаторов.

## Что не проверяется

- Полноценный WebRTC/RTP-звонок с аудиопакетами, микрофоном и демонстрацией
  экрана. Проверяются только voice grant, WebSocket join и soundboard.
- Рендеринг и клики в браузере, каждый экран React и визуальная корректность UI.
- Исчерпывающие комбинации ролей/наследования ACL, ошибки всех некорректных
  входных данных и многопользовательские гонки операций.
- Сохранность данных после перезапуска контейнеров и долговременная деградация.

Для них нужен отдельный интеграционный/нагрузочный набор, а не минутный CHECK.
